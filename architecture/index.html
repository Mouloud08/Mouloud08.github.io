Une plateforme pour lancer de petites apps, sûres par défaut

Chaque nouvelle app reçoit la connexion, les rôles, une base Postgres protégée, un site et un déploiement contrôlé. Conçue et codée avec mes agents IA, elle part d'une règle : l'agent qui écrit une app ne doit jamais pouvoir affaiblir la sécurité des autres.

Pourquoi la construire

Je voulais créer beaucoup de petites apps avec des agents IA, sans réécrire à chaque fois la connexion, les permissions et le déploiement, et sans frais tant qu'il n'y a pas de vraies données personnelles.

Elle remplace une plateforme maison plus ancienne (API sur Cloud Run et MongoDB Atlas). Refaire le socle sur MongoDB a été écarté : pas de Row Level Security, et l'authentification, les autorisations, le CRUD, le temps réel et le stockage auraient tous été à refaire à la main.

Le chemin d'une requête

Il n'y a pas de serveur d'application. Postgres est le serveur : les données, les permissions et la logique métier y vivent.

  1. Navigateur

    Le site envoie le jeton de la personne connectée et une clé publique.

  2. API de données

    Supabase expose le schéma de l'app et transmet l'identité à Postgres.

  3. Row Level Security

    Chaque règle appelle platform.has_role() ou platform.uid().

  4. Résultat

    La base renvoie seulement ce que ce rôle a le droit de voir ou de modifier.

Du pull request à la production

L'app fournit des données (site compilé, app.json, migrations). Toutes les étapes sensibles tournent sur le code du hub.

  1. Pull request

    3 contrôles : build, base de données, recherche de secrets. Base jetable, tests pour chaque rôle, pour un non-membre et pour un anonyme.

  2. Fusion sur main

    La CI repasse et produit le site compilé.

  3. deploy-app

    Le hub vérifie que ce commit a une CI verte, applique les migrations, contrôle le catalogue, puis publie le site et le teste.

  4. Préproduction

    Les tests de bout en bout se font ici.

  5. promote-prod

    Lancement manuel, avec confirmation tapée à la main. Exactement le même commit et les mêmes fichiers partent en production.

Comment la sécurité tient

La CI donne un retour rapide, mais elle exécute du code que l'app contrôle. Ce qui fait foi, c'est la base de données et le hub.

Migrations limitées

Chaque app a un rôle qui ne peut modifier que son schéma.

Une migration qui touche une autre app échoue.

Mot de passe à usage unique

À chaque déploiement, une connexion dédiée reçoit un mot de passe valable 30 minutes au plus, puis elle est refermée. Le rôle propriétaire ne se connecte jamais.

Pas d'accès permanent à la base, et le mot de passe en clair n'arrive jamais au serveur.

Contrôle du catalogue

Après les migrations, le hub vérifie : RLS sur chaque table, aucune règle ouverte, vues sécurisées, aucun droit pour les anonymes, extensions autorisées seulement.

Une violation bloque la publication du site. Le contrôle repasse chaque jour.

Secrets au hub seulement

Dans des environnements limités à main, avec un jeton Supabase distinct par projet.

Un jeton de préproduction qui fuite n'atteint pas la production.

Pas de code serveur dans les apps

Aucune Edge Function côté app.

Une fonction Supabase reçoit l'accès complet à la base et pourrait lire tous les schémas.

Deuxième facteur

La console des membres exige un deuxième facteur (TOTP) pour gérer les rôles. Les changements sont journalisés.

Un mot de passe volé ne suffit pas pour se donner des droits.

Les décisions et leurs raisons

PostgREST plutôt qu'un service CRUD maison
Avec une clé secrète, ce service contournerait la RLS. Avec le jeton de l'utilisateur, il ne serait qu'un intermédiaire plus lent.
Le hub n'installe ni ne compile le code d'une app
Il reprend le site déjà compilé par la CI, sans lancer ce code dans une tâche qui détient des secrets.
Migrations additives seulement
Supprimer ou renommer une colonne est refusé en CI. Une migration déjà appliquée ne peut pas être modifiée : son empreinte est enregistrée.
Code partagé copié depuis le modèle
Un paquet npm privé exigerait un jeton à large portée partout.
Passage en production avec confirmation tapée
Sur les dépôts privés avec GitHub Pro, l'approbation obligatoire par un relecteur n'est pas disponible.
Tâche quotidienne keep-alive
Les projets gratuits se mettent en pause après 7 jours de faible activité. Elle sert aussi à refaire les contrôles de sécurité.

Ce que j'ai coupé, et les limites

Un audit indépendant, mené par un modèle d'IA en lecture seule, a noté le premier jalon 6/10 : sécurité solide, mais environ 7 900 lignes de plateforme pour zéro app. J'ai gardé la sécurité et coupé le reste pour livrer une première app.

Reporté

  • API partagée et tâches planifiées, tant qu'aucune app n'en a besoin
  • Déclenchement automatique des déploiements : ils sont lancés à la main
  • Aperçus de pull request
  • Sauvegardes automatiques : l'essai de sauvegarde chiffrée et de restauration a réussi, mais elles ne tournent pas encore

Limites assumées

  • Isolation entre apps : elle tient face aux utilisateurs et aux migrations, pas face à du code d'app malveillant dans la base
  • Une app avec de vraies données personnelles aura donc son propre projet, avec l'évaluation prévue par la Loi 25
  • Plafonds de l'offre gratuite : 500 Mo de base par projet, 3 000 minutes de CI par mois
