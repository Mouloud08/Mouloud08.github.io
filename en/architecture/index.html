A platform for launching small apps, secure by default

Every new app gets sign-in, roles, a protected Postgres database, a site and a controlled deployment. Designed and coded with my AI agents, it starts from one rule: the agent writing an app must never be able to weaken the security of the others.

Why I built it

I wanted to create many small apps with AI agents, without rewriting sign-in, permissions and deployment every time, and at no cost while there is no real personal data.

It replaces an older home-made platform (an API on Cloud Run with MongoDB Atlas). Rebuilding the foundation on MongoDB was ruled out: no Row Level Security, and authentication, authorisation, CRUD, realtime and storage would all have been hand-built again.

The path of a request

There is no application server. Postgres is the server: data, permissions and business logic live there.

  1. Browser

    The site sends the signed-in person's token and a public key.

  2. Data API

    Supabase exposes the app's schema and passes the identity to Postgres.

  3. Row Level Security

    Every rule calls platform.has_role() or platform.uid().

  4. Result

    The database returns only what this role may see or change.

From pull request to production

The app provides data (built site, app.json, migrations). Every sensitive step runs on the hub's code.

  1. Pull request

    3 checks: build, database, secret scan. A throwaway database, with tests for each role, a non-member and an anonymous user.

  2. Merge to main

    CI runs again and produces the built site.

  3. deploy-app

    The hub checks this commit has green CI, applies the migrations, checks the catalog, then publishes the site and tests it.

  4. Staging

    End-to-end tests happen here.

  5. promote-prod

    Started by hand, with a typed confirmation. Exactly the same commit and files go to production.

How the security holds

CI gives fast feedback, but it runs code the app controls. What counts is the database and the hub.

Limited migrations

Each app has a role that can only change its own schema.

A migration touching another app fails.

One-time password

Each deployment gives a dedicated login a password valid for 30 minutes at most, then closes it. The owner role never logs in.

No standing database access, and the plaintext password never reaches the server.

Catalog check

After the migrations, the hub verifies: RLS on every table, no open rule, secure views, no rights for anonymous users, allowed extensions only.

A violation blocks publishing the site. The check runs again every day.

Secrets in the hub only

In environments limited to main, with a separate Supabase token per project.

A leaked staging token cannot reach production.

No server code in apps

No Edge Functions on the app side.

A Supabase function gets full database access and could read every schema.

Second factor

The member console requires a second factor (TOTP) to manage roles. Changes are logged.

A stolen password is not enough to grant yourself rights.

The decisions and why

PostgREST rather than a home-made CRUD service
With a secret key, that service would bypass RLS. With the user's token, it would only be a slower middleman.
The hub never installs or builds an app's code
It takes the site CI already built, without running that code in a job that holds secrets.
Additive migrations only
Dropping or renaming a column is refused in CI. An applied migration cannot be edited: its fingerprint is recorded.
Shared code copied from the template
A private npm package would need a broad token everywhere.
Production gate with a typed confirmation
On private repos with GitHub Pro, required reviewer approval is not available.
Daily keep-alive job
Free projects pause after 7 days of low activity. It also re-runs the security checks.

What I cut, and the limits

An independent audit, run by a read-only AI model, scored the first milestone 6/10: sound security, but about 7,900 lines of platform for zero apps. I kept the security and cut the rest to ship a first app.

Deferred

  • Shared API and scheduled jobs, until an app needs them
  • Automatic deployment triggers: they are started by hand
  • Pull request previews
  • Automatic backups: the encrypted backup and restore trial passed, but they do not run yet

Accepted limits

  • Isolation between apps: it holds against users and migrations, not against malicious app code in the database
  • So an app with real personal data will get its own project, with the assessment Quebec's Law 25 calls for
  • Free tier ceilings: 500 MB of database per project, 3,000 CI minutes a month
